# Contact FAQ Dynamic CMS Design

## Goal

Extend the categorized Contact FAQ redesign with a dedicated bilingual CMS editor. Editors must be able to create, rename, reorder, and safely remove shared FAQ categories, then create, edit, reorder, delete, and recategorize Korean and English FAQ content without editing raw JSON.

The public C + C1 FAQ layout, Contact Hero, Contact form, submission behavior, and SEO fields remain unchanged.

## Content Model

Categories use one shared stable identifier and one shared order across Korean and English. Each locale stores its localized label under the same identifier:

```ts
type ContactFaqCategory = {
  id: string;
  label: string;
};

type ContactFaqItem = {
  category: string;
  question: string;
  answer: string;
};
```

The Korean and English Contact content each receive a `faqCategories` array. The arrays must contain the same IDs in the same order, while their labels remain localized. The Korean and English FAQ arrays must also have the same length, order, and category assignments; question and answer copy remains locale-specific.

The existing category IDs remain stable:

- `consultation`
- `design`
- `business`
- `sports`

New category IDs are generated by the CMS editor and are not directly editable. The legacy `faqCategoryLabels` object remains synchronized as a rollback and compatibility surface.

## CMS Editor

The Contact page receives a dedicated FAQ editor above the normal locale panels. The generic page editor excludes `faqCategories`, `faqCategoryLabels`, and `faqs` so they are not rendered twice.

### Category Management

Each category row contains:

- its current order;
- Korean label;
- English label;
- move-up and move-down actions;
- a delete action.

Editors can add categories. The client creates a stable internal ID and immediately makes the new category available in every FAQ category selector. At least one category must remain.

Deleting a category that is referenced by one or more FAQs is blocked. The editor shows the number of referencing FAQs and asks the editor to move or remove them first. Category deletion never silently moves or deletes content.

### FAQ Management

Each FAQ card contains:

- its current order;
- one shared category selector;
- Korean question and answer fields;
- English question and answer fields;
- move-up and move-down actions;
- a delete action.

Editors can add FAQ cards. Category options update immediately when category labels or category order change.

## Submission And Validation

The dedicated editor submits one structured JSON payload containing shared category identity/order and aligned bilingual FAQ drafts. The server parses and validates the payload before the normal page payload is saved.

Validation requires:

- at least one category;
- unique, safe, non-empty category IDs;
- non-empty Korean and English category labels;
- every FAQ category reference to resolve to a submitted category;
- non-empty Korean and English questions and answers;
- unique questions within each locale;
- aligned Korean and English FAQ order and category assignments.

The normalized result is written only to the Contact main content group. Hero, form, SEO, and unrelated CMS content are preserved. Both locale payloads receive the same category and FAQ ordering. `faqCategoryLabels` is derived from the normalized categories for backward compatibility.

Validation errors use localized CMS feedback and do not partially save content.

## Public Rendering And Legacy Compatibility

The public FAQ component uses `faqCategories` as the authoritative chapter order when available. It supports any valid CMS category ID and continues to render the desktop four-chapter archive layout and mobile C1 accordion behavior for the default data.

Compatibility behavior remains fail-visible:

- if `faqCategories` is absent, the four legacy category labels and fixed order are synthesized;
- known legacy questions without a category are classified by their exact Korean or English question text;
- a FAQ whose category is missing from the category list is rendered in an exceptional localized `Other` chapter;
- no question or answer is dropped from server-rendered HTML.

## Migration And Rollout

The Contact FAQ migration remains dry-run by default and applies only with `--apply`. It is extended to write aligned `faqCategories`, synchronized compatibility labels, categorized Korean content, and complete English translations.

The migration must:

- require exactly the known twenty unique questions in both locales;
- abort before backup or update on unknown, missing, or duplicate questions;
- preserve Korean answers and all unrelated Contact content;
- back up `cms_pages` and the Contact row before applying;
- update through one guarded transaction;
- remain idempotent after the new dynamic structure is present.

Release order:

1. Merge the verified implementation to `main` and push it.
2. Confirm the AWS production checkout is clean and can fast-forward.
3. Rebuild the production `next` and `nginx` services.
4. Run the Contact FAQ migration dry-run on AWS.
5. Apply only when Korean and English each match twenty items.
6. Run the migration again to confirm it reports already up to date.
7. Verify the public Korean Contact page and the Contact CMS editor without altering other CMS content.

The English public route may continue redirecting to Korean while the existing `englishEnabled` feature flag is disabled. English content is still managed and validated in CMS.

## Verification

Automated coverage includes:

- category creation, renaming, reordering, and minimum-one enforcement;
- category deletion protection while referenced;
- FAQ creation, deletion, reordering, and category changes;
- bilingual payload validation, normalization, save, and reload behavior;
- dynamic public category ordering and exceptional `Other` rendering;
- legacy fixed-category compatibility;
- migration dry-run, backup, apply, idempotency, and fail-closed cases;
- Korean and English content counts, completeness, and preserved business facts;
- server-rendered FAQ content and stable ARIA relationships.

Before release, run the complete source test suite, ESLint, and a production build. Browser verification covers the Contact CMS editor, the Korean public Contact page at 1440px and 375×812, category and FAQ interactions, horizontal overflow, console errors, and production HTTP/container health.
